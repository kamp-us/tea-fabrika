## The question, as the plan writes it

**A second GitHub App, so that push tokens and main's bypass never sit on one App.** merger's admin merge in a sev needs an App on main's bypass list, and a push token carries its App's bypass, so T1 keeps tokens refusing while the App it vends from holds any bypass. The plan asks for a second App, made and installed by the owner only when merger's admin merge is to go live (Rollout step 7), never before. The existing `fabrikalfa` App keeps the webhook, the programs and the push tokens, and stays on no bypass list. The new App holds only main's bypass and only what an admin merge needs (`contents: write`, `pull_requests: write`), has no webhook, is used by merger alone, and keeps its key in the Secrets Store (0537). Yes; or no, and admin merges stay with `land.ts merge --admin` for good while merger's admin path, built and tested on memory layers in slice 4, never runs live; or yes with the jobs swapped, so the new App vends push tokens and the existing App takes the bypass. Lean: yes, as written, 70% sure. Why: it keeps T1 true without giving up merger's admin merge; the App on the bypass list does one rare, powerful thing, so its key is the one most worth keeping narrow; and every push and draft pull request stays `fabrikalfa[bot]`'s, the identity 0401 gives agents. The known way splits the same: Octo STS (https://github.com/octo-sts/app) is a GitHub App of its own whose one job is minting narrowed tokens, and its README tells an org that cannot use the hosted one to "self-host octo-sts with their own GitHub App". The swapped branch follows Octo STS more literally, but pushes would then come from a second bot name while commits still name `fabrikalfa[bot]`. What it costs: one App made and installed once by the owner, a few minutes once and no recurring prompt; a second private key in the Secrets Store and in any key rotation; sev admin merges show the second App's bot as the merger in the history; and `@kalfa/provider-github`'s credentials Layer takes two Apps, a small change at Rollout step 7. What would settle the doubt: a `vector:` read of GitHub's ruleset API showing that a bypass is per actor and that no token narrows it (from memory today), recorded before Rollout step 7; and the owner's word on whether a second bot name on sev admin merges is fine in the history.
